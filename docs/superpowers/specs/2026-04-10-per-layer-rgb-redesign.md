# Iris LM Per-Layer RGB Indication Redesign

**Date:** 2026-04-10  
**Status:** Design Approval

---

## Context

The `vial_custom` keymap currently has a working per-layer RGB indication system (`rgb_layers.c`/`.h`), but it relies on a fragile hardcoded LED index approach generated by an external Python script. The implementation has accumulated technical debt:

- Hardcoded LED arrays must be manually regenerated when the keymap changes
- Separate C module adds complexity without corresponding benefit
- Commented-out tap dance C functions (conflicting with Vial's dynamic system)
- Unused activation delay define
- Backup files and dead code cluttering the directory
- Secondary half (right side) does not receive layer state, so RGB indication doesn't work on both halves

**Goal:** Rebuild from scratch using standard QMK practices. Replace hardcoded arrays with the documented dynamic keycode-checking approach (`keymap_key_to_keycode` + `KC_TRNS` filtering). Extend from 4 layers to 7 for testing headroom. Ensure the design is maintainable, stable, and requires no external tooling.

## Design: Clean RGB Layer Indication

### Layers (7 total)

| Layer | Name | Purpose | Colour | HSV Hue |
|-------|------|---------|--------|---------|
| 0 | _MAIN | Base QWERTY | (default animation) | — |
| 1 | _FN1 | Numbers/symbols | Green | 85 |
| 2 | _FN2 | Function keys + RGB controls | Cyan | 128 |
| 3 | _FN3 | Admin (EE_CLR) | Red | 0 |
| 4 | _FN4 | (empty, test) | Blue | 170 |
| 5 | _FN5 | (empty, test) | Orange | 21 |
| 6 | _FN6 | (empty, test) | Purple | 213 |

New layers 4–6 are stubs (all `KC_TRNS`), ready to be populated during experimentation.

### Architecture

**Single `keymap.c` file** — no separate RGB module needed.

**RGB Indication Hook:**  
`rgb_matrix_indicators_advanced_user(uint8_t led_min, uint8_t led_max)`

- Runs after animations render, overlaying colour on top
- Receives `led_min`/`led_max` for correct split keyboard batching (avoid flickering on secondary half)
- Iterates matrix positions (row, col), looks up the keycode on the active layer via `keymap_key_to_keycode(layer, pos)`
- Only colours keys where `keycode > KC_TRNS` (filters out transparent pass-throughs)
- Uses HSV color space (saturation full 255, value follows user's RGB brightness)
- Early exit if on layer 0 (base layer uses normal animation, no override)

**RGB Toggle:**  
`RGB_LYR` custom keycode (`QK_KB_0`) — press to toggle layer indication on/off at runtime. Minimal footprint (~5 lines in `process_record_user`).

**Tap Dance:**  
Keep `TD(0)` and `TD(1)` references in the keymap. Remove the compiled C functions (`td_esc_ctrl_finished`, etc.) — Vial's dynamic tap dance system handles these at runtime. The `VIAL_TAP_DANCE_ENTRIES 32` setting in config.h enables Vial GUI to configure them.

### New keymap.c Structure

1. Layer enum with `_MAIN, _FN1, _FN2, _FN3, _FN4, _FN5, _FN6`
2. Custom keycode enum: `RGB_LYR = QK_KB_0`
3. Layer colour lookup table (HSV triplets)
4. `rgb_matrix_indicators_advanced_user()` — iterates matrix, checks keycodes, colours non-transparent keys
5. `process_record_user()` — toggles `rgb_layer_indication_enabled`
6. Keymap array: 7 layers, layers 4–6 are all `KC_TRNS`

Code volume: ~150 lines keymap.c (down from 200+ split across modules).

**Existing Layers 0–3:** Keymaps are preserved exactly as they currently exist in `vial_custom/keymap.c`. Only layers 4–6 are new stubs.

### Vial Integration

- `vial.json` unchanged (layer count driven by `DYNAMIC_KEYMAP_LAYER_COUNT`)
- Vial GUI can configure tap dances dynamically
- Vial GUI can reorder keymap at runtime
- RGB indication automatically reflects GUI changes (no Python script needed)

## Config Details

**Split Keyboard Sync:**  
`SPLIT_LAYER_STATE_ENABLE` ensures the secondary (right) half receives layer state from the primary half. Without it, the secondary half's RGB logic would always see layer 0, breaking the indication.

**Tapping Term Per Key:**  
`TAPPING_TERM_PER_KEY` is enabled so home-row mods and tap dances can have different tapping windows (commented-out hook in current code can be re-enabled if needed).

**Tap Dance via Vial:**  
Vial's dynamic tap dance system replaces hardcoded `tap_dance_actions[]`. The `TD(0)` and `TD(1)` keycodes stay in the keymap, but their behavior is configured in the Vial GUI, not in C code.

- Home row mods respond with correct tapping term

## Not In Scope

- Backlight support: investigated and confirmed not needed (no separate backlight circuit; underglow already working as part of RGB matrix)
- Uncommented tap dance C functions: not required with Vial's dynamic system; can be re-enabled if per-key tapping terms need C-level precision
- Optimization: per-frame iteration cost is negligible (54 matrix position checks); no threading/caching needed
- Animations beyond coloring: use Vial GUI's animation selector for effects

## Rollback Plan

If issues arise:
1. Keep the old `vial_custom` keymap as a git branch or backup
2. Fall back to plain `vial` keymap (4 layers, no per-layer RGB)
3. Cherry-pick working pieces if needed

All changes are isolated to `keymaps/vial_custom/` — no changes to the keyboard's base config or other keymaps.
